# Voxiva Desktop: функции CLI в приложении

## Намерение

Сделать desktop-приложение полноценным графическим способом работы с Voxiva CLI: пользователь выбирает проект и модель, ведёт и продолжает сессии, настраивает провайдеров, выбирает план и может просматривать и применять изменения файлов. Встроенный терминал остаётся частью приложения и сохраняет все возможности CLI, включая команды, для которых пока нет отдельного графического экрана.

## Цели

- Основные действия CLI доступны из понятных экранов и кнопок приложения.
- Чат использует тот же каталог моделей, провайдеры, планы, файлы и конфигурацию, что и CLI.
- API-ключи можно добавить, посмотреть в маскированном виде и удалить из приложения; открытые ключи не возвращаются renderer-процессу.
- Сессии переживают перезапуск приложения и возобновляются с историей сообщений.
- История проектов, тема, язык, модель и план сохраняются через существующее хранилище Voxiva.
- `update` и `doctor` доступны из графического интерфейса; desktop-приложение проверяет GitHub Releases и предлагает обновление с подтверждением. Встроенный терминал остаётся доступен для полного CLI и исправления проблем установки.
- Видимые кнопки выполняют действие, либо отключены с понятным объяснением, если действие сейчас невозможно.

## Не входит в первый этап

- Удаление или замена CLI и его TUI.
- Повторная реализация shell-команд и редких TUI-операций в Electron, если они уже полноценно работают во встроенном терминале.
- Автоматический запуск произвольных команд проекта без явного действия пользователя.
- Изменение формата существующих файлов конфигурации и авторизации.

## Как это должно работать

### Главное окно

Сохраняется уже выбранная композиция Voxiva: боковая панель, центральный чат, композер, выбранный проект, модель, план, Git-ветка и встроенный терминал. Подключение ключей открывается в приложении, а не отправляет пользователя в терминал. Список моделей обновляется после добавления/удаления провайдера; недоступные модели не выбираются. Переключение Build/Ship/Check/Explore влияет на тот же сохранённый план и системную инструкцию, что в CLI.

### Проекты и рабочие файлы

Выбор, создание и повторное открытие проекта используют системный диалог и хранилище workspaces CLI. Приложение показывает последние существующие проекты, выбранную папку и ветку Git. Добавление файлов в контекст ограничено текущим проектом. Предложения модели остаются на просмотре до явного применения; отклонение предложения не меняет файлы.

### Провайдеры и модели

Настройки показывают поддерживаемые CLI провайдеры, состояние подключения без открытого ключа, поля для подключения и действия для замены/удаления. Секреты принимаются только через валидируемый IPC, сохраняются существующим `saveAuth`, а renderer получает лишь статусы и маскированные значения. Каталог использует существующие `listCatalog`, `listFreeCatalog` и `listOpenCodeCatalog`/проверки доступности.

### Сессии и чат

Новая сессия очищает только текущий контекст. Сохранённые сессии доступны в боковой панели и могут быть продолжены с сообщениями, проектом, планом и моделью. Чат сохраняется через существующее `src/sessions/store.ts`; сообщения и контекст ограничиваются существующими лимитами. Остановка, потоковый ответ и подтверждение правок остаются частью одного потока.

### Доступ к оставшимся функциям CLI

Кнопка терминала всегда открывает встроенный CLI в текущей папке проекта. Через него доступны `run`, `ship`, `doctor`, `install`, `update`, `config`, все slash-команды и продвинутые действия TUI (история, память, очередь, diff, undo/redo, экспорт, темы, язык и прочее). Для частых действий интерфейс приложения предлагает графические элементы. Если системная диагностика или обновление CLI требуют терминальной команды, приложение показывает точную команду и кнопку открытия терминала.

### Настройки, темы и язык

Тема и язык приложения синхронизируются с общим конфигом CLI и восстанавливаются после перезапуска. Системная тема остаётся вариантом `auto`. Настройки не должны теряться при открытии нового окна.

## Ограничения и защита данных

- Electron IPC валидирует тип, размер и допустимые значения всех входных данных.
- Главный процесс остаётся единственным владельцем файловой системы и API-ключей.
- Нельзя записывать секреты в логи, ошибки, localStorage, события UI или ответ `app:state`.
- Операции применения файлов используют существующий `prepareEdits`/`applyEdits` и защиту путей.
- CLI и desktop-бинарник обновляются разными механизмами и не должны выдавать себя друг за друга. Desktop-обновления публикуются в GitHub Releases вместе с установщиками для Windows, macOS и Linux. На Windows и Linux приложение предлагает загрузку и установку с подтверждением; на macOS без подписи оно открывает страницу релиза с подходящим образом установки.
- Существующий встроенный терминал и формат хранилищ остаются совместимыми.

## Условия готовности

- Пользователь может с нуля открыть проект, подключить провайдера, выбрать доступную модель и план, отправить запрос, остановить ответ, просмотреть/применить/отклонить правки.
- После перезапуска доступны выбранные проект, тема, язык, настройки модели/плана и список прошлых сессий; сессия продолжается с правильным контекстом.
- Удаление провайдера убирает его модели из доступного выбора, а подмена API-ключа не раскрывает старый ключ.
- Кнопки сессий, проектов, модели, плана, темы, терминала, настроек и обновления проходят путь до результата либо показывают конкретную причину блокировки.
- Тег версии собирает и публикует установщики всех поддерживаемых платформ в GitHub Release; установленная desktop-версия находит новый релиз и показывает обновление до начала загрузки.
- CLI-команды, не продублированные графическим интерфейсом, остаются доступными во встроенном терминале.
- Windows, macOS и Linux сохраняют запуск и встроенный терминал без зависимости от системного Swift или Node.js.

## Решения, оставленные исполнителю

- Разбить реализацию по независимым этапам: безопасное IPC и настройки провайдера; сохранение сессий/история проектов; темы/язык/диагностика и UX обновления.
- Переиспользовать сервисы `src/` вместо повторной реализации в `apps/desktop`.
- Для каждого добавленного поведения сначала зафиксировать контракт тестом; затем проверить сборку приложения и основной тестовый набор CLI.
- Не добавлять зависимости, если возможностей Electron и существующего CLI достаточно.
